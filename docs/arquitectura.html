La regla para no perderte

app/

"¿Qué se ve?"

Cada carpeta con un page.tsx es una URL. Ej: app/(app)/pagos/page.tsx → /pagos. Los paréntesis (app) solo agrupan; no aparecen en la URL. Los corchetes [id] son una parte variable (/inversiones/abc123).

actions.ts

"¿Qué se guarda?"

Junto a cada página hay un actions.ts con las funciones que escriben en la base: crear, editar, borrar. Son las que llaman los botones de los formularios.

lib/

"¿Cómo se calcula?"

Aquí viven las matemáticas, separadas de la pantalla. Si un número del dashboard está mal, casi seguro el culpable está en investments.ts o aggregations.ts.

Cómo viaja un clic por el repo

Ejemplo: abres /pagos y agregas un pago.

  1. middleware.ts confirma que hay sesión.
  2. (app)/layout.tsx dibuja la barra lateral.
  3. pagos/page.tsx pide los pagos a Supabase (con lib/supabase/server.ts) y usa lib/format.ts para mostrar los montos.
  4. Envías el formulario → pagos/actions.ts guarda la fila en recurring_payments.
  5. La página se refresca sola con el pago nuevo.

Cómo el repo se une a la base de datos

El código (src/) y la base (supabase/) viven en lugares distintos: el código corre en tu PC y la base en la nube de Supabase. La carpeta supabase/ del repo solo guarda los SQL como recibo. Si cambias el código para usar una columna nueva, tienes que correr también su migración en Supabase, o la app falla.

Estado de git hoy: rama main; las migraciones 003–005 y la página de detalle de inversiones aún no están guardadas en un commit.

1. Visión general

Tres piezas: el navegador (lo que ves), Next.js (la app) y Supabase (login + base de datos). Hoy corre en tu PC (localhost:3000); Vercel aún no está configurado.

Next.js

Frontend + backend en uno

Las páginas se arman en el servidor, ya con los datos. Por eso no hay una API aparte: cada página llama directo a Supabase.

Supabase

Tu base de datos y tu login

Guarda usuarios y tablas. No programaste un servidor de base de datos: Supabase te lo da hecho.

Vercel

Pendiente

Es donde se publicaría la app para abrirla desde cualquier lado. Hoy solo funciona en tu computador.

¿Frontend y backend juntos? ¿Y los endpoints?

Sí: en Next.js es un solo proyecto y se despliega en un solo sitio. A diferencia de React + Node/Express, no tienes dos carpetas ni dos servidores. Pero el código sigue dividido en dos mundos.

Servidor (Node)

page.tsx, layout.tsx, actions.ts, route.ts, middleware.ts, lib/. Aquí están las llaves (.env.local) y los cálculos. Nada de esto llega al navegador.

Navegador

Solo lo que lleva "use client": DashboardCharts.tsx (Recharts dibuja en pantalla) y ConfirmDeleteButton.tsx (necesita el clic).

2. Cómo funciona Supabase aquí

Supabase hace dos trabajos: saber quién eres (Auth) y guardar tus datos de forma privada (Postgres + RLS).

Login paso a paso

  1. Escribes email y contraseña en /login (o /signup).
  2. Una Server Action manda esos datos a Supabase Auth.
  3. Supabase te devuelve una sesión y se guarda en una cookie del navegador.
  4. En cada visita, el middleware lee la cookie y pregunta a Supabase "¿quién es?" (auth.getUser()).
  5. Sin sesión en /dashboard, /inversiones o /pagos → te manda a /login. Con sesión en /login → te manda al dashboard.

RLS: por qué nadie ve tus datos

RLS = Row Level Security. Es una regla dentro de la base de datos, en cada tabla:

using (auth.uid() = user_id)

Significa: "solo devuelve las filas cuyo user_id sea el del usuario que pregunta". Aunque alguien tuviera la llave pública, la base de datos le filtra todo lo que no es suyo. Cada fila nueva se guarda con tu user_id.

Al subir a Vercel hay que copiarlas allí también.

Ciclo de un dato (ejemplo: agregar una inversión)

  1. Llenas el formulario en /inversiones y das "Agregar".
  2. createInvestment (server action) verifica tu sesión y arma el objeto con parseInvestment, que limpia los campos que no aplican al tipo (p. ej. un CDT no guarda datos de crédito).
  3. Hace insert en la tabla investments con tu user_id. Si falla, lanza el error.
  4. revalidatePath le dice a Next.js que vuelva a pedir los datos y la lista se actualiza sola.

4. Diagrama Entidad-Relación

Hay 3 tablas tuyas, todas colgadas del usuario (auth.users, que maneja Supabase). La línea punteada es un enlace "informal" por texto, no una llave foránea real.

5. Qué es cada tabla y cómo funciona

investments

Tu dinero puesto a trabajar

Una fila por inversión. El campo category decide qué datos importan:

CDT: monto, tasa, inicio y vencimiento.
Vivienda: precio de compra, valor actual, crédito (monto, tasa, plazo, día de pago).
Fondo / acciones / otro: monto y valor actual.

ownership_pct (p. ej. 50) es tu parte si es con un socio; todos los totales usan solo tu parte.

recurring_payments

Facturas con fecha

Arriendo, servicios, cuotas. Cada una tiene due_date. Si vence en ≤5 días se marca como urgente. El botón ✓ "pagado" mueve la fecha un mes adelante, así la fila se reutiliza cada mes.

cash_flows

Lo que entra y sale cada mes

kind = ingreso o gasto. frequency: monthly cuenta siempre; once solo si su fecha cae en el mes actual. Con property puedes ver el neto por apartamento.

Moneda: las tres tablas usan el tipo currency_code (COP, USD, EUR). Las migraciones 001–005 en supabase/migrations/ son el historial de cambios que fuiste corriendo en el SQL Editor.

6. Tarjetas y cálculos

Regla de oro: las monedas nunca se suman entre sí (no hay conversión EUR↔USD↔COP). Cada moneda tiene su propia tarjeta. Antes de todo, myShare() multiplica monto, valor, precio y crédito por ownership_pct/100.

Cuota mensual del crédito monthlyPayment

Sistema francés (cuota fija). La tasa es efectiva anual, se pasa a mensual:

i     = (1 + tasaEA)^(1/12) − 1
cuota = P · i / (1 − (1+i)^−n)

P = monto del crédito, n = plazo en meses. Si la tasa es 0: P / n.

Ejemplo: 100.000.000 al 12 % E.A., 240 meses → i ≈ 0,949 % → cuota ≈ 1.059.000.

Valor de hoy currentValue

vivienda → current_value ?? purchase_price ?? amount
otros    → current_value si lo escribiste
CDT      → amount · (1 + tasaEA)^(días/365)
           (días desde start_date; se congela
            en maturity_date si ya venció)
sin datos→ amount

Ejemplo CDT: 10.000.000 al 12 % E.A. tras 180 días → 10.000.000 · 1,12^(180/365) ≈ 10.575.000.

Avance del crédito creditProgress

k      = meses desde start_date (máx. plazo)
saldo  = P·(1+i)^k − cuota·((1+i)^k − 1)/i
intereses pagados = cuota·k − (P − saldo)

Dice cuántas cuotas llevas, cuánto debes hoy y cuánto de lo pagado fueron intereses. Es estimado: no incluye seguros ni abonos extra.

Próximo pago nextPaymentDate

Con el payment_day (1–31) busca la primera fecha igual o posterior a hoy; en meses cortos usa el último día del mes (31 → 28 en febrero).

7. Cómo funcionan las gráficas

Todas son de Recharts en components/DashboardCharts.tsx. La página (servidor) prepara los datos con lib/aggregations.ts y se los pasa a la gráfica (navegador), que solo dibuja.

Dona

Inversiones por moneda

sumByCurrency recorre las inversiones financieras y suma amount en un mapa {moneda → total}. Cada porción = una moneda (COP morado, USD ámbar, EUR verde azulado).

Dona

Por tipo · Por plataforma

groupSum filtra a la moneda principal (COP si existe, si no la primera) y suma por categoría o por plataforma, de mayor a menor. Sin plataforma → "Sin plataforma".

Área

Pagos próximos por mes

paymentsByMonth crea 6 "cajones" (este mes + 5) y mete cada pago en el cajón de su due_date, sumando por moneda. Pagos fuera de esos 6 meses no se dibujan.

Flujo de datos de una gráfica

Supabase ──select──▶ dashboard/page.tsx ──▶ myShare() (tu %)
                                        ──▶ aggregations.ts (suma / agrupa)
                                        ──props──▶ DashboardCharts.tsx ──▶ SVG en pantalla

8. Cosas a vigilar (honestas)

  • Dashboard vacío = error silencioso: si falta una migración (p. ej. 005) o una columna, la consulta de inversiones falla. La página lanza el error en vez de mostrar datos a medias; revisa que 001–005 estén corridas en Supabase.
  • /ingresos no está en el middleware: la lista de rutas protegidas solo incluye dashboard, inversiones y pagos. Los datos siguen protegidos por RLS (sin sesión no devuelve filas), pero conviene agregarla para que redirija a login.
  • cash_flows no tiene política de update: hoy solo se puede crear y borrar, no editar.
  • Sin conversión de monedas: no existe un "patrimonio total" único; cada moneda va aparte a propósito.
  • Arriendo ↔ vivienda por texto: si el nombre del apartamento en Ingresos no es idéntico al nombre de la inversión, el arriendo sale en 0.
  • Cuotas y saldos son estimados: sin seguros, comisiones ni abonos extra.
  • supabase/schema.sql solo trae investments y recurring_payments originales; cash_flows y las columnas nuevas viven en las migraciones.

9. Seguridad: qué protege tus datos

Como no hay una API propia con reglas, la protección real es el RLS de Supabase más la sesión. Lo demás ayuda, pero no es el candado.

Las capas, de la más débil a la que de verdad protege

CapaDóndeQué hace¿Es seguridad real?
1. Middlewaremiddleware.tsManda a /login si no hay sesiónComodidad Solo redirige; no impide que se pidan datos.
2. Sesiónauth.getUser()Pregunta a Supabase quién eres (valida la cookie, no se fía de ella)Identidad Sin sesión no hay usuario.
3. user_id desde el servidoractions.tsAl crear, el user_id lo pone el servidor, no el formularioBuena práctica El usuario no puede elegir "ser" otro.

Qué es público y por qué no importa

La URL de Supabase y la ANON_KEY viajan al navegador (por eso empiezan con NEXT_PUBLIC_). Cualquiera puede verlas. Es seguro solo porque RLS está activo: con esa llave, la base devuelve únicamente las filas del usuario con sesión.

La llave peligrosa sería la service_role: se salta el RLS. En el repo no se usa (la busqué) y nunca debe llevar el prefijo NEXT_PUBLIC_ ni subirse a git.

Ejemplo: alguien intenta borrar lo tuyo

  1. Un usuario malicioso con su propia cuenta llama a deletePayment con el id de un pago tuyo.
  2. El servidor ejecuta delete … where id = … con la sesión de él.
  3. RLS agrega por dentro and user_id = su_id. Ninguna fila coincide.
  4. Resultado: se borran 0 filas. Tu dato sigue ahí.

Las Server Actions son endpoints públicos aunque no los hayas escrito: cualquiera con sesión puede llamarlos con los datos que quiera. Por eso la defensa no puede estar en el formulario.

Puntos débiles reales, de mayor a menor importancia

  1. Confirmar que RLS está activo en Supabase. El repo guarda el SQL, pero lo que cuenta es lo que corriste en la nube. Revisa en Supabase → Table Editor que cada tabla diga "RLS enabled", y mira el Security Advisor. Si una tabla estuviera sin RLS, cualquiera con la ANON_KEY leería todo.
  2. Las políticas de update/delete no se refuerzan en el código. updatePayment, deletePayment, updateInvestment y deleteCashFlow filtran solo por id. Hoy RLS lo cubre; si algún día se desactivara una política, el código no tendría un segundo seguro. Agregar .eq("user_id", user.id) sería una defensa extra barata.
  3. Casi no hay validación en el servidor. Los actions.ts convierten con Number() y aceptan lo que llegue; la base rechaza lo inválido (enum, check), pero el usuario vería un error crudo. createPayment, updatePayment, deletePayment y markPaymentAsPaid además ignoran los errores sin avisar. No es riesgo de fuga, sí de datos que "no se guardan" sin que lo notes.
  4. /ingresos fuera del middleware. Sin sesión no ve datos (RLS), pero ve la pantalla vacía en vez de ir al login.
  5. Cuenta y contraseña. La fortaleza de contraseña y la confirmación por correo se configuran en Supabase → Authentication, no en el código. Hoy el registro pide confirmar el correo; conviene tener una contraseña mínima razonable y no abrir el registro si la app es solo para ti.
  6. Al desplegar en Vercel: copia solo las dos variables públicas; .env.local ya está ignorado por git (verificado) y .env.local.example solo trae marcadores de posición.
Resumen: la arquitectura es segura si RLS está activo y la service_role nunca sale del servidor. Lo primero que haría es el punto 1; es un chequeo de 2 minutos en el panel de Supabase.
